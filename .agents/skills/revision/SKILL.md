# Ревизия кода за период

Отчёт отвечает на два вопроса: **что происходило в коде** и **какие в этом проблемы**. Каждая находка перепроверена в коде. Читатель отчёта диффа не видел — отчёт самодостаточен и вводит в курс дела.

## 0. Инициализация каталога

Перед началом убедись в наличии каталога `.agents/revisions/` и файла `.agents/revisions/README.md`. Если отсутствуют — создай:
```markdown
# Ревизии проекта
Здесь хранятся периодические отчёты ревизий кодовой базы (скилл `revision`).
- Формат: `ГГГГ-ММ-ДД_<ветка>_<диапазон>.md`. Не коммитить автоматически, отправляет человек.
- Прошлые отчёты не редактируются; ответы разработчиков фиксируются в разделе «Комментарии разработчика».
```

## 1. Определение диапазона

**Порядок приоритета:** явный аргумент вызова → однозначный контекст текущей ветки → короткий вопрос оператору при неоднозначности.

Если диапазон не задан или неоднозначен, задай один короткий вопрос:
> *«Какой диапазон проверить: с прошлой ревизии, за период (например, 7d/30d), конкретную ветку или задачу?»*

### Интерпретация свободных ответов:
- **«сегодняшние правки»:** с `00:00` текущего дня до `HEAD` на текущей ветке (`--since="today 00:00"`).
- **«правки по задаче <ID>»** (например, `123`):
  1. Найти описание задачи по `<ID>` в `.agents/local/tasks/` или `.agents/tasks/`;
  2. Найти ветку `*<ID>*` или коммиты через `git log --grep="<ID>"`;
  3. База — `git merge-base main <ветка>` (или точка ответвления).
- **«ветка <имя> за неделю»:** коммиты выбранной ветки за 7 дней (`--since="7 days ago"`).
- **`7d` / `30d` / `<N> коммитов` / `sha1..sha2`:** вычисляются напрямую.
- **«с прошлой ревизии» / дефолт на основной ветке:** взять дату и конечный SHA из заголовка последнего файла в `.agents/revisions/`. Анализировать коммиты строго от зафиксированного SHA до текущего `HEAD`. Сам текст прошлого отчёта на этом шаге **не читать**, чтобы исключить предвзятость и замыливание взгляда. Если отчётов нет — спросить период.

Перед анализом зафиксируй: точный `BASE` SHA, конечный `HEAD` SHA и число коммитов.

## 2. Сбор истории и diff

```bash
# Для периода на основной ветке брать только по первому родителю (без шума чужих веток):
BASE=$(git rev-list -1 --first-parent --before="<дата>" HEAD)
# Для ветки задачи:
BASE=$(git merge-base main HEAD)

git log $BASE..HEAD --no-merges --format='%h %ad %an %s' --date=short
git diff $BASE..HEAD --stat
```

Дифф целиком в контекст не грузить. По `--stat` выбери ключевые изменённые файлы и читай конкретные фрагменты через `git show` / чтение файлов вместе с окружающим контекстом.

## 3. Анализ: картина изменений (своей головой)

До поиска проблем восстанови суть работы исключительно по коду и diff:
1. **Направления:** сгруппируй коммиты по 1–4 логическим темам (характер: новый функционал / багфикс / переделка / рефакторинг; объём; суть человеческими словами «что было → что стало → зачем»).
2. **Заметное:** новые эндпоинты/URL, изменения контрактов API, новые параметры конфигурации/env, новые зависимости, удалённое/переименованное.
3. **Авторы:** кто в каких направлениях работал (карта ответственности).

## 4. Поиск новых находок «чистым взглядом» (своей головой)

Ревизор ищет проблемы **исключительно в новом коде диапазона**, не заглядывая в прошлые отчёты и не пользуясь подсказками:
- **Критерий:** реальное неверное поведение, потеря данных, утечка ресурсов, нарушение контрактов/безопасности, сбои, гонки данных. Не включать: стиль, опечатки, форматирование, рутину линтера.
- **Инвариант:** каждая находка должна быть проверена на актуальном коде `HEAD` и иметь воспроизводимый сценарий «вход/состояние → отказ». Отделять подтверждённое от предположений.
- **Лимит:** не более 7 новых находок по убыванию серьёзности (Blocker / Major / Minor). Остальное — одной строкой в «Прочее».
- Зафиксируй черновик: направления работы, заметное и список свежих находок.

## 5. Сверка с прошлым отчётом (динамика и преемственность)

Только после того, как новые находки найдены и зафиксированы, открой предыдущий отчёт из `.agents/revisions/` (если он есть):
1. **Что исправлено:** проверь, устранены ли в текущем диффе замечания из прошлого отчёта. Если исправлены — зафиксируй в разделе `## Динамика` (`- Исправлено: ... (найдено <дата>)`).
2. **Комментарии разработчика:** прочитай раздел `## Комментарии разработчика` прошлого отчёта. Если автор аргументированно возразил по какому-то вопросу и код подтверждает его правоту — учти это контекстное знание и не поднимай вопрос повторно.
3. **Переходящие находки (П1..ПN):** старые неисправленные дефекты перенеси в раздел `## Переходящие находки` с пометкой *(впервые <дата>, N-я ревизия подряд)*. Если среди найденных тобой в шаге 4 находок оказался старый незакрытый баг — перенеси его в переходящие, освободив место в основном списке для новых находок.

## 6. Дополнительный контроль через SonarQube (усиление отчёта)

После ручного анализа и сверки с историей проверь возможность усилить отчёт статическим анализом:

1. **Проверка наличия и доступности:**
   - Есть ли `sonar-project.properties` в корне репозитория?
   - Заданы ли переменные `SONAR_HOST_URL` и `SONAR_TOKEN` в `.env` (или окружении)?
   - Если конфигурации нет, переменные отсутствуют или сервер SonarQube недоступен — **пропусти этот шаг без ошибок**: отчёт ревизора уже самодостаточен.
2. **Запуск по проверяемой области:**
   - Определи изменённые файлы:
     `CHANGED=$(git diff --name-only --diff-filter=d $BASE..HEAD | paste -sd, -)`
   - Для ревизии диапазона/ветки/задачи (при непустом `$CHANGED`) запускай сканер только по затронутым файлам:
     `docker run --rm --network host --env-file <REPO>/.env -v "$PWD:/usr/src" sonarsource/sonar-scanner-cli -Dsonar.inclusions="$CHANGED"`
   - Если ревизия проводилась по всему проекту целиком без диапазона — запускай без `-Dsonar.inclusions`.
   - Если `SONAR_HOST_URL` указывает на `localhost` или `127.0.0.1`, обязателен флаг `--network host`.
3. **Усиление отчёта:**
   - Если анализ успешно завершился — добавь в раздел `### Заметное` статус Quality Gate и число новых дефектов.
   - Проверь список предупреждений Sonar: если сканер нашёл реальный дефект (NPE, утечка дескриптора, уязвимость), который ускользнул при ручном анализе, перепроверь его на коде `HEAD`, составь сценарий отказа и добавь в раздел «Находки» (в рамках общего лимита).
   - Ложные срабатывания (false positives) и формальные code smells сканера в отчёт не включай.

## 7. Формирование отчёта

Загрузи шаблон из `.agents/skills/revision/templates/report.md`, заполни все разделы фактическими данными и сохрани отчёт:
- **Запрет любых локальных/временных путей и служебных секций:** отчёт коммитится в git и читается людьми.
  Категорически запрещено:
  1. Упоминать любые абсолютные или временные пути хоста (`/tmp/...`, `/home/...`, `/srv/...`), пути из `.gitignore` (`.env`, `.agents/local/`, `.agents/tasks/`, `.agents/workers/`) и имена локальных черновиков/заметок оператора;
  2. Добавлять в отчёт служебные секции: таблицы соответствия ТЗ или черновикам, отчёты о своих действиях, записки для `CONTEXT.md` воркера.
  Отчёт строго завершается разделом «Комментарии разработчика». Все ссылки в тексте — исключительно на версионируемые файлы репозитория относительно корня (`файл:строка`, например `src/index.js:42`) либо внешние задачи трекера (`#123` или `https://tracker.example.com/123` при наличии внешнего трекера в проекте).
- **Путь:** `.agents/revisions/<YYYY-MM-DD>_<ветка>_<диапазон>.md` (при коллизии добавить время `_HHMM`).
- **Сам отчёт не коммить** — отправку в git выполняет человек или оркестратор по поручению.
- **При вызове внутри команды оркестратора (воркер Ревизор):** вернуть полный текст отчёта координатору для сохранения и регистрации на доске.

## 8. Ответ оператору

Сообщить: путь к созданному отчёту; краткую суть работы за период (1–2 фразы); число находок по серьёзности (Blocker / Major / Minor); что чинить первым. Не пересказывать текст отчёта целиком.
