## Ограничения инструментов (важно)

- **Субагент не пишет текстовые отчёты и память в файлы** — возвращает текстом, записывает оркестратор (сразу, с пометкой «со слов <имя>, не перепроверено», если не проверял). Код, коммиты, макеты, снимки, скрипты стендов воркер создаёт сам.
- **В worktree нет игнорируемых файлов** (`.agents/workers`, `.agents/tasks`, `.agents/local`). В задании воркеру — абсолютные пути к ним в основной рабочей копии.
- **Воркеры не общаются напрямую.** Сообщения друг другу — через раздел «Обсуждение» задачи; оркестратор переносит их туда из ответов и передаёт адресату.
- **Память = файл.** Живого воркера продолжают сообщением (контекст сохраняется), но на **≥ 100k токенов** — пересоздают (см. «Память воркера»).

## Ветки

- **Базовая ветка** = текущая ветка основной рабочей копии на момент запуска оркестратора (проверить `git branch --show-current`), если автор не назвал другую. Защищённые ветки (см. «Особенности проекта») — без явного подтверждения автора не трогать и базой не брать.
- Воркер-исполнитель: `git worktree add -b work/<slug> .agents/worktree/<slug> <база>`, только там, коммиты в свою ветку. Незакоммиченное в базе воркер не увидит — если оно относится к задаче, сказать автору.
- Ветки и worktree воркеров создаёт и вливает оркестратор: `git merge --ff-only work/<slug>` в основной копии; база ушла вперёд — `git -C <wt> rebase <база>`, конфликт → `--abort` и к автору. После — `git worktree remove`, `git branch -d`.
- push — никогда (если в «Особенностях проекта» не сказано иное).

## Запуск воркеров и доставка результата

В таблице «Состав» в столбце «Роль» каждого воркера записываются его харнес и модель в формате `<роль> (<харнес>: <модель>)` (например: `разработчик (codex: gpt-6.1-terra medium)`, `ревьюер (agy: gemini-3.8-flash-medium)`, `ревьюер (opencode: opencode/big-pickle)`). Руководство по выбору моделей по ролям (планы О / К / Б и ограничения квот) — в `.agents/skills/orchestrator/models.md` (первоисточник на машине — `/srv/ai/vllm/.agents/eval/ORCHESTRATOR_MODELS.md`).
- **Единая точка настройки модели:** при запуске воркера оркестратор всегда сверяется со столбцом «Роль» в «Составе» и запускает именно указанный там харнес и модель (если указано `default` — флаг `--model`/`-m` опускается; уровень рассуждений по умолчанию — `medium`). Чтобы сменить модель воркеру, достаточно поправить её в таблице «Состав». Проверка доступных на машине моделей (`codex debug models`, `agy models`, `opencode models`) выполняется только при добавлении/редактировании воркера или при ошибке квоты, а не при каждом старте сессии.
- **Формат упоминания воркера и учёт токенов:** оркестратор во всех ответах автору, в шапках задач (`owner:`), в «Журнале», в `done/README.md` и в `orchestrator/CONTEXT.md` всегда пишет имя воркера вместе с харнесом, моделью и (после завершения сессии) расходом токенов через запятую: `Имя (<харнес>: <модель>, <новые>/<всего> ток.)` (например, `Терра (codex: gpt-6.1-terra medium, 88k/7.8M ток.)`, а при нескольких сессиях в одной задаче — через запятую: `75k/2.4M ток., 88k/7.8M ток.`), где `<новые>` = `uncached_in + out`, `<всего>` = `total` с учётом `cache_read` по всем шагам (`~/.codex/sessions/...`, `~/.gemini/antigravity-cli/brain/.../transcript.jsonl`, `opencode export` / `opencode stats`). От воркеров требовать в начале каждого отчёта указывать свой `<харнес>: <модель>`.
- **Перенос оттестированных задач в `done/`:** как только `merged`-задача прошла приёмку у тестировщика и все найденные замечания вынесены в новые задачи в `.agents/tasks/`, оркестратор сразу (без отдельной команды автора) переносит проверенную задачу с вложениями в `.agents/tasks/done/` и записывает её в `.agents/tasks/done/README.md`.

Перед выдачей проверить среду запуска главной сессии оркестратора:
- **Если оркестратор запущен внутри Orca** (заданы `ORCA_TERMINAL_HANDLE` или `ORCA_WORKSPACE_ID`, либо `TERM_PROGRAM=Orca`): выполнить `orca skills get orchestration`, завести/продолжить Run (`orca orchestration run-create` / `run-use`) и запускать воркеров через `orca orchestration worker-start` (передавая `--worktree path:<wt>` или `current`, `--agent <codex|opencode|claude|antigravity>`, `--model <модель>`, `--effort medium` для codex, `--task-title`, `--spec`), ожидая завершения через `orca orchestration check --wait` и освобождая терминал через `orca orchestration worker-release`.
- **Если оркестратор запущен из обычного терминала вне Orca** (`ORCA_TERMINAL_HANDLE` и `ORCA_WORKSPACE_ID` пустые): **Orca не использовать**, даже если она запущена на машине.
  - В Claude использовать штатную фоновую задачу с уведомлением о завершении; это относится и к команде `codex exec` / `agy -p` / `opencode run`, а не только к встроенным субагентам.
  - В Codex и Antigravity при доступных субагентах (`collaboration.spawn_agent` / `invoke_subagent`) запускать CLI харнес воркера внутри отдельного субагента-обёртки, который дожидается завершения CLI, читает итоговый отчёт и возвращает его главной сессии со штатным уведомлением:
    - **Antigravity (`agy`):** `cd <wt> && agy -p --mode auto --model <модель из Состава> --add-dir <папка воркера> "<задание>"`
    - **Codex:** `codex exec -s workspace-write -C <wt> --add-dir <папка воркера> -m <модель> -c 'model_reasoning_effort="medium"' -o /tmp/<имя>-last.txt "<задание>" < /dev/null`
    - **opencode:** `cd <wt> && opencode run -m <модель из Состава> --auto "<задание>"`
  - Обычные `exec_command` с `session_id`, shell `&`, `nohup` и файл `-o` сами по себе не являются механизмом уведомления. Не оставлять такой процесс единственным способом получить ответ после завершения хода главной сессии.
  - Если механизма уведомлений нет, вести выполнение в активной сессии до результата, с короткими ожиданиями и обновлениями автору. Не обещать автоматического уведомления, которого инструмент не предоставляет.

При запуске записать в задачу и память оркестратора имя воркера, способ доставки (`Orca: run_id / dispatch_id` или `CLI: subagent_id / session_id`) и worktree. По уведомлению прочитать результат, записать переход задачи и сообщить автору итог. Завершение процесса само по себе не означает успешное выполнение задачи.

## Задачи

Шаблон — `.agents/skills/orchestrator/templates/task.md`. Id — время создания `ГГГГММДДччммсс`, slug — латиница, он же имя ветки `work/<slug>`.

Статусы (`status:` в шапке): `idea` → `discussion` → `ready` → `in-progress` → `review` → `merged` (в базе) → `released`. Сбоку: `blocked`, `dropped`.
Доска — не отдельный файл, а сводка по шапкам: `grep -H -m1 '^status:' .agents/tasks/*.md .agents/tasks/*/task.md`.

Пишет в задачу только оркестратор:
- шапку (статус, исполнитель, ветка, worktree, база) — при каждом переходе;
- «Журнал»: `ГГГГ-ММ-ДД — кто — что` (одна строка на событие: выдана, сдана, ревью круг N, влита, решение автора);
- «Обсуждение»: `ГГГГ-ММ-ДД Имя → Имя: текст` — вопросы и ответы между воркерами и автором;
- решения автора — дословно или близко, с датой.

## Роли и когда их звать

| Роль | Когда | Доступ к коду |
|---|---|---|
| Продакт | идея автора → задачи; разбор бэклога; раз в релиз «что дальше» | только чтение |
| Архитектор | крупная или рискованная задача — план до разработки; спорные решения | только чтение |
| Дизайнер | до разработки UI-задачи — макеты; после — сверка со снимками | без worktree (макеты в задачу) |
| Разработчик | задача `ready` | запись в worktree |
| Ревьюер | каждый раз, когда разработчик сдал; всегда новый, чистый | только чтение (diff) |
| Переводчик | после задач с новыми текстами — пачкой; тексты для релиза | запись в worktree |
| Сеошник | тексты витрин и метаданные (README, сайт, магазин) — до/после правок; аудит перед выпуском | запись в worktree (аудит — только чтение) |
| Тестировщик | приёмка merged-задач и предрелизный смоук | стенды в `files/`, код не правит |
| Безопасник | перед выпуском: всё, что изменилось с прошлого релиза | только чтение |

Задачу разработчику даю по специализации (столбец «Специализация»); нет подходящего — свободному; все заняты — спросить автора, ждать или добавить нового (имя из пула).

## Цикл задачи

1. **Постановка.** Идею автора — сам в задачу или через продакта; крупное — через архитектора; UI — через дизайнера. Неясно — вопросы автору до выдачи.
2. **Выдача.** Проверить, что параллельные задачи не правят одни и те же места (иначе — последовательно). Задание воркеру:
   - «Тебя зовут <имя>. Сначала прочитай `<абс. путь>/.agents/workers/<роль>/<имя>/AGENTS.md`, затем `CONTEXT.md` и задачу `<абс. путь>`.»
   - суть и критерии готовности, worktree, ветка, база, ограничения проекта, как проверить, что вернуть.
   В задаче: `status: in-progress`, исполнитель, журнал; в «Составе»: `занята`.
3. **Ревью.** Ревьюер (новый) получает: задачу, worktree, `git -C <wt> diff <база>...HEAD`, ограничения проекта, свой `AGENTS.md` (там чек-лист частых ошибок).
4. **Правки (≤ 3 кругов).** Находки перепроверить по коду, ложные — отбросить с причиной.
   - blocker/major → тому же разработчику (сообщением; при ≥ 100k — пересоздать), затем новое ревью.
   - только minor → автору; решаем вместе: править или в бэклог (задача `idea`).
   - после 3 кругов остались blocker/major или стороны расходятся по сути → к автору.
5. **Слияние** — когда нет blocker/major и автор решил по minor (или сказал «вливай»). Статус `merged`, журнал, «Состав»: `свободна`. Память воркера обновить (см. ниже).
6. **Отчёт автору:** что сделано, коммиты, круги ревью, исправлено/отклонено и почему, что не проверено.

## Память воркера (`CONTEXT.md`)

- Это не история (она в задачах), а то, что нужно, чтобы продолжить без объяснений: карта своей области кода, принятые решения и почему, стенды и как запускать, известные хвосты, ссылки на задачи. 1–3 экрана.
- Обновляю после каждой сданной задачи: прошу у воркера записку (текстом), **переписываю** `CONTEXT.md` целиком, а не дописываю.
- Перед каждым сообщением воркеру смотрю его токены. ≥ 100k: дождаться конца текущего шага → записка → `CONTEXT.md` → новый субагент с тем же именем («сначала прочитай AGENTS.md и CONTEXT.md»). Автору — что пересоздан.
- Ревьюер не помнит задач — только чек-лист типичных находок в своём `AGENTS.md`; пополняю его, когда находка повторяется.
- Своё состояние (что в работе, у кого, какие ветки, что ждёт автора) — в `.agents/workers/orchestrator/CONTEXT.md`, обновлять при каждом переходе задачи.

## Документация проекта (`.agents/docs`)

Устойчивое знание, полезное всем (устройство кода, как проверять, решения автора, которые надолго), — из записок воркеров переношу в `docs/` и говорю автору. Коммит — по правилам проекта (обычно только по слову автора).
